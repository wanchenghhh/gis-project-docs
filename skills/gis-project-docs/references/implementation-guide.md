# 实施方案指南

## 基础框架

根据项目范围、用途与复杂度合并或拆分以下主题，不把此顺序作为固定要求：
1. 项目背景与任务依据：立项背景、建设依据、项目边界。
2. 建设目标与内容：用户、业务目标、任务分解、建设范围及成果。
3. 建设要求：功能、性能、运行与交付要求；指标保留单位和约束条件。
4. 总体方案：系统组成、架构、数据与业务流程、接口和运行环境；深度按文档用途确定。
5. 实施计划：各项任务、方法、职责、阶段工作产品、完成标准。
6. 进度与组织：里程碑、依赖、资源、职责与协调安排。
7. 质量与过程管理：评审、测试、问题闭环、配置及变更控制；按实际组织要求选择。
8. 交付与后续服务：成果清单、验收安排、培训及运维。
9. 要求追溯：把合同或任务要求对应到方案章节及交付成果，可作为表格或附件。

用户明确的客户提交结构作为本次任务约束处理。封面、摘要、关键词、签署页、修改记录及目录按实际文档管理要求选择，不默认强制齐套。项目、系统和文档标识及版本采用当前项目规则，签署信息依据真实记录。

## 条件章节

- 新建与升级：有既有成果或分期任务时，区分复用、新增、升级和外部单位责任，不将旧成果算作本次新建成果。
- 数据建设：有生产、治理或迁移任务时，说明来源、类型、范围、时空基准（适用时）、处理流程、存储、更新、质检与成果；不要把所有 GIS 项目限定为网格项目。
- 算法模型：有模型研发时，说明目标、输入输出、研发验证安排及成果；参数或效果指标由资料提供。
- 集成：涉及外部系统时，说明接口边界、交换数据、依赖、联调责任与安排。
- 部署：有交付部署时，说明环境、组件位置、网络与资源约束；不复用样例设备配置。
- 硬件：有采购任务时，说明清单、数量、采购检验、安装和交付安排。
- 试验：有试验任务时，说明目的、场景、方法、评价条件和报告成果。
- 专项要求：合同或组织明确要求时再使用自主可控、专项质量属性、专门测评等内容，不默认套用样例中的标准和程序。

## 段落与表格写法

每项工作回答：做什么、怎么做、谁负责、何时完成、形成什么成果、怎样确认完成。未知字段列入待补清单。

常用表格按需要选择：任务及实施安排表、里程碑表、角色职责表、成果清单、接口清单、要求追溯表。表格的任务、名称和时间应能互相对应。

总体架构说明服务于当前项目，避免用大量通用技术科普替代设计。方案尚未确定时，区分备选建议与已批准方案。

## SFT-02 模板补充的编写要点

需要技术论证深度时，读 [SFT-02 模板提炼要点](sft02-writing-patterns.md)。将其作为内容覆盖参考，章节按项目合并或拆分：
- 总体设计解释建设思路和原则如何服务业务场景；总体技术方案解释架构、组成、流程、接口和环境。两者内容简单时合并，避免重复。
- 分别说明用户业务活动与数据流转，复杂时提供图示并解释节点、参与方、模块和流向。
- 子系统或模块按需要说明目的、组成、功能、相关指标、输入输出和实现方式；不为常规功能强行编造算法。
- 对确有技术难点的项目描述问题、约束、解决途径及验证方法，不将技术名词本身当作创新或难点。
- 接口表记录发送方、接收方、类型和内容；环境表记录真实配置、版本、数量或资源分配。未知信息待补，备选技术不得写成已确定配置。
- 要求追溯同时检查每个要求是否被方案覆盖，以及方案中的实施承诺是否有需求或批准依据；可以采用一份映射表完成双向检查，无需复制两张表。

扩展技术内容时仍保持实施方案深度，不自动扩展为完整详细设计文档。具体字段和图示使用条件见链接，不默认加载原始Word模板。
