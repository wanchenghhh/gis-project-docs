# 项目工作总结与研制工作总结指南

## 基础框架

自适应模式根据受众与项目阶段调整：
1. 项目基本情况：背景、目标、范围和要求，简要交代原任务。
2. 实施或研制完成情况：过程、阶段活动、评审与测试、各项任务实际完成情况。
3. 要求符合性：目标、功能、性能、数据、硬件等要求与实际结果、考核方式和证据对应。
4. 质量与过程管理情况：已经实施的质保、配置、变更与问题闭环；不将计划措施直接改成完成事实。
5. 主要建设成果：文档、软件、数据、硬件及试验成果，记录名称、版本、数量和交付状态。
6. 问题、差异与经验：实际与计划的差异、已批准变更、遗留问题和经验，有资料时写实，无资料时待补。
7. 下一步安排：验收、整改、移交、培训或运维，按实际阶段选用。

专项质量、算法验证、硬件检验、数据质检、跨项目集成等只在当前项目涉及时展开。技术攻关内容适度概述；详细技术总结属于后续专项能力，不自动扩写成技术总结报告。

## 写作逻辑

每项内容采用“原要求—实际完成情况—成果—验证依据—差异或遗留问题”。阶段活动可用“时间—活动—工作产品—评审/测试结果—问题处理”组织。

摘要概括报告实际覆盖的内容，不列正文没有的章节。已完成仅表示工作状态，不自动表示指标达标、成果交付或验收通过。

合同验收前的报告应准确说明当前阶段：完成验收测试、具备验收条件、等待验收决定各有不同含义。未提供正式验收结论时不得写“已通过合同验收”。下一步计划使用计划语气。

## 证据与数据

性能符合性表建议字段：要求编号、原指标与条件、实际结果及单位、测试环境与数据规模、考核方式、证据位置、符合性状态。未收到测试报告时，标明结果来自用户提供的报告正文，不能声称已经独立验证。

吞吐量指标必须有处理数量和耗时；响应时间要对应数据规模与查询条件；并发指标要说明连接或请求的口径。不能仅凭“测试测评”四字确认结论。

成果清单应与建设范围、完成情况和交付记录一致。未交付和已完成应分别记录；结果说明以资料为准，不为表格齐整而全部填写“符合”。
